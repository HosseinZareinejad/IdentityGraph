# موتور تطبیق هویت VectorID

سیستم VectorID یک پلتفرم پیشرفته تطبیق هویت (Entity Resolution) است که هدف آن یافتن پروفایل‌های تکراری، نویزدار یا دارای غلط املایی در یک پایگاه داده بزرگ از کاربران است. این سیستم با ترکیب روش‌های جستجوی معنایی (Semantic Search) و الگوریتم‌های قطعی متنی (Deterministic String Matching)، می‌تواند با وجود داده‌های ناقص یا اشتباه، محتمل‌ترین کاندیداها را با دقت بالایی شناسایی کند.

## معماری سیستم

معماری این سیستم از سه لایه اصلی تشکیل شده است:

### ۱. پردازش و ذخیره‌سازی داده‌ها (Ingestion)
در این لایه، داده‌های متنی پیش‌پردازش می‌شوند. یکی از مهم‌ترین اقدامات، یکسان‌سازی حروف فارسی و عربی (تبدیل «ي» و «ك» به «ی» و «ک») است تا خطای ناشی از تفاوت کدگذاری کاراکترها در جستجوها از بین برود. 
سپس برای هر فیلد متنی مهم (نام، شهر و بیوگرافی)، یک بردار معنایی مستقل (Vector Embedding) توسط مدل‌های زبانی چندزبانه (Multilingual Sentence Transformers) تولید شده و در پایگاه داده Qdrant با فرمت Multi-Vector ذخیره می‌گردد.

### ۲. جستجوی هوشمند (Retrieval)
هنگام دریافت یک درخواست جستجو، سیستم همزمان ۳ بردار مستقل برای پارامترهای ارسالی تولید کرده و پایگاه داده Qdrant را به صورت موازی جستجو می‌کند (Union Retrieval). این رویکرد تضمین می‌کند که حتی در صورت وارد کردن اطلاعات بسیار کوتاه (مثلاً یک کلمه به عنوان بیوگرافی)، وزن معنایی فیلدهای دیگر مانند نام، افت نکرده و فرد مورد نظر به سرعت به عنوان کاندیدا بازگردانده می‌شود.
علاوه بر بردارهای معنایی، جستجوی دقیق (Exact Match) روی شماره تماس و ایمیل نیز برای افزایش پوشش کاندیداها انجام می‌گیرد.

### ۳. امتیازدهی نهایی (Ensemble Scoring)
لیست کاندیداهای یافت‌شده، وارد لایه نهایی امتیازدهی می‌شوند. در این لایه از ترکیب الگوریتم Jaro-Winkler (برای نام و نام خانوادگی)، الگوریتم Levenshtein (برای نام کاربری و مشخصات کوتاه) و شباهت کسینوسی (برای متون بلند مانند بیوگرافی) استفاده می‌شود. نتیجه نهایی، درصدی بین ۰ تا ۱۰۰ است که میزان انطباق قطعی را نشان می‌دهد.

### پیچیدگی زمانی (Time Complexity)
معماری موتور VectorID به گونه‌ای طراحی شده است که با رشد پایگاه داده افت سرعت نداشته باشد. پیچیدگی زمانی کل سیستم در زمان اجرای یک درخواست برابر با **(O(log N** است (N = تعداد رکوردهای پایگاه داده):
1. **تبدیل متن به بردار (Embedding):** به دلیل محدود بودن طول ورودی‌ها، زمان اجرا ثابت یا **(O(1** است.
2. **جستجوی معنایی (Vector Search):** به لطف استفاده از ساختار داده HNSW در Qdrant، جستجو در بین میلیون‌ها بردار با پیچیدگی لگاریتمی **(O(log N** انجام می‌شود.
3. **جستجوی قطعی روی Payload:** فیلترهای شماره و ایمیل در Qdrant ایندکس شده‌اند و پیچیدگی لگاریتمی **(O(log N** دارند.
4. **امتیازدهی نهایی (Scoring):** از آنجا که تعداد کاندیداهای ورودی به این لایه محدود به یک عدد ثابت (حدوداً ۱۶۰ نفر) است، الگوریتم‌های فاصله‌سنجی رشتهای (O(M² برای هر کدام، در مجموع پیچیدگی **(O(1** (زمان ثابت) دارند و به حجم دیتابیس وابسته نیستند.

بنابراین، زمان پاسخ‌دهی سیستم حتی برای دیتابیس‌های چند ده میلیونی، زیر ۱۰۰ میلی‌ثانیه باقی می‌ماند.

## چالش‌های پروژه و راه‌حل‌ها

در طول توسعه این پروژه با سه چالش اساسی مواجه شدیم:

### چالش اول: تداخل حروف عربی و فارسی
در آزمایش‌های اولیه متوجه شدیم الگوریتم‌های محاسبه فاصله رشته‌ای (مانند Jaro-Winkler) برای نام‌هایی که از نظر بصری یکسان هستند اما با کیبورد عربی تایپ شده‌اند (مانند "ريحانه" و "ریحانه") خطای بالایی نشان می‌دهند.
**راه‌حل:** یک ماژول نرمال‌ساز مبتنی بر کتابخانه `hazm` در لایه پیش‌پردازش و همچنین در ورودی API پیاده‌سازی شد تا تمامی ورودی‌ها پیش از هرگونه پردازش، به حروف استاندارد فارسی تبدیل شوند.

### چالش دوم: افت دقت در جستجوی متون کوتاه
در ابتدا، تمام فیلدهای یک پروفایل به یک جمله واحد تبدیل شده و سپس بردار معنایی آن تولید می‌شد. این رویکرد باعث شد وقتی کاربر اطلاعات بسیار کوتاهی وارد می‌کند، فاصله معنایی آن با پروفایل اصلی (که بیوگرافی طولانی داشت) بسیار زیاد شود و سیستم فرد را پیدا نکند.
**راه‌حل:** تغییر ساختار پایگاه داده از Single-Vector به Multi-Vector. با این کار، نام‌ها به طور مستقل با نام‌ها، و شهرها به طور مستقل با شهرها سنجیده می‌شوند و مشکل تقلیل وزن معنایی (Dilution) برطرف گردید.

### چالش سوم: تضاد نسخه‌های کلاینت Qdrant
نسخه جدید کتابخانه پایتون `qdrant-client` در ارسال درخواست‌های مربوط به بردارهای نام‌دار (Named Vectors) به سرورهای محلی، ساختار متفاوتی تولید می‌کرد که منجر به خطای `400 Bad Request` در جستجوی معنایی می‌شد.
**راه‌حل:** برای ایجاد پایداری کامل و وابستگی کمتر به نسخه‌های مختلف پکیج، بخش مربوط به جستجوی بردارهای نام‌دار در ماژول `retriever.py` دور زده شد و درخواست‌ها به صورت مستقیم از طریق HTTP REST API (با استفاده از پکیج `httpx`) به پایگاه داده Qdrant ارسال گردید.

## ساختار پروژه

*   `ingestion.py`: اسکریپت اصلی برای خواندن مجموعه داده، تولید بردارها و درج آن‌ها در پایگاه داده Qdrant.
*   `api/main.py`: سرور FastAPI که نقطه پایانی (Endpoint) تطبیق هویت را ارائه می‌دهد.
*   `src/vector_db.py`: مدیریت اتصالات و تنظیمات Qdrant.
*   `src/retriever.py`: منطق جستجوی موازی و استخراج کاندیداها از دیتابیس.
*   `src/scorer.py`: پیاده‌سازی الگوریتم‌های Ensemble Scoring.
*   `src/text_utils.py`: توابع نرمال‌سازی و پیش‌پردازش متن.
*   `ui/`: رابط کاربری مبتنی بر React و Tailwind CSS.

## نیازمندی‌ها و راه‌اندازی

برای اجرای این پروژه، به ابزارهای زیر نیاز دارید:
*   Docker (برای اجرای پایگاه داده Qdrant)
*   Python 3.11+
*   Node.js 18+ (برای اجرای رابط کاربری)

### مرحله اول: اجرای دیتابیس Qdrant
ابتدا پایگاه داده Qdrant را از طریق داکر اجرا کنید:
```bash
docker run -p 6333:6333 -p 6334:6334 \
    -v $(pwd)/qdrant_storage:/qdrant/storage:z \
    qdrant/qdrant
```

### مرحله دوم: تنظیمات محیط پایتون و بارگذاری داده‌ها
یک محیط مجازی پایتون ایجاد کرده و پیش‌نیازها را نصب کنید:
```bash
python -m venv venv
# در ویندوز:
.\venv\Scripts\activate
# در لینوکس/مک:
# source venv/bin/activate

pip install -r requirements.txt
```

سپس اسکریپت Ingestion را اجرا کنید تا داده‌ها مدل‌سازی و وارد Qdrant شوند (این مرحله ممکن است به دلیل دانلود مدل زبانی و پردازش داده‌ها، چند دقیقه زمان ببرد):
```bash
python ingestion.py
```

### مرحله سوم: اجرای سرور بک‌اند (API)
پس از اتمام موفقیت‌آمیز مرحله قبل، سرور FastAPI را اجرا کنید:
```bash
uvicorn api.main:app --host 0.0.0.0 --port 8000
```

### مرحله چهارم: اجرای رابط کاربری (Frontend)
یک ترمینال جدید باز کرده و وارد پوشه `ui` شوید:
```bash
cd ui
npm install
npm run dev
```

اکنون می‌توانید از طریق مرورگر به آدرس `http://localhost:5173` مراجعه کرده و از داشبورد حرفه‌ای سیستم VectorID استفاده کنید.
